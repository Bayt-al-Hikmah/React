In the previous workshop, we built a task manager where users could add tasks, mark them as completed, and delete them. We managed the entire task collection using React state, which allowed the interface to respond whenever the data changed.

However, our application still has an important limitation: its data exists only while the application is running. When we refresh the browser, the tasks disappear because React state is not automatically saved between page loads.

## React and the Outside World

So far, most of our examples have worked with information already available inside React. In our task manager, for example, we used `useState` and `useReducer` to manage the task collection. Whenever a user added or deleted a task, React updated the state and rendered the interface using the new data.

Everything happened inside the React application. However, real applications rarely operate in isolation. They need to exchange information with servers, interact with the browser, and sometimes respond to events generated by external services.

Consider what our task manager might need as it grows. Instead of starting with an empty task collection, it could retrieve the user's existing tasks from a backend API. It might also allow users to select a theme and remember that preference when they return. In other situations, the application may need to change the browser tab title, focus an input field, or listen for messages arriving through a WebSocket connection.

Although these operations are different, they share something important: they involve systems that React does not directly control.

React manages the interface and its state, but it does not automatically manage network requests, browser storage, timers, or external subscriptions. We therefore need a way to connect our components to these systems and keep them synchronized with the current state of the application.

This is where `useEffect` becomes useful.

## Understanding `useEffect`

React provides a Hook called `useEffect` that allows a component to synchronize with an external system.

Before looking at the code, let's understand what synchronization means.

Imagine that we have a component displaying the user's name:

```tsx
function Profile({ name }: { name: string }) {
  return <h1>Welcome, {name}</h1>;
}
```
React knows how to display the heading because it is part of the component's JSX. Whenever the `name` prop changes, React renders the component again and updates the heading.

However, suppose we also want the browser tab title to display the user's name. The browser tab title is not part of our JSX; it belongs to the browser document. React does not automatically update it when the `name` prop changes.

We therefore need to tell the browser when its title should change. This is a good situation for `useEffect`:

```tsx
import { useEffect } from 'react';

function Profile({ name }: { name: string }) {
  useEffect(() => {
    document.title = `Welcome, ${name}`;
  }, [name]);

  return <h1>Welcome, {name}</h1>;
}
```
When the component renders, React first updates the interface. After the commit, the Effect runs and changes the browser tab title.

Notice the second argument:

```tsx
[name]
```
This is called the **dependency array**. It tells React which reactive values the Effect uses and needs to stay synchronized with.

In our example, the Effect uses the `name` prop, so we include it in the dependency array. Whenever `name` changes, React runs the Effect again and updates the browser title accordingly.

The dependency array is important because it allows React to determine when an Effect needs to run again. Without it, React would run the Effect after every commit, even when the values relevant to the external system had not changed.

### Understanding the Dependency Array

The dependency array determines when React needs to run an Effect again. There are three common situations, and understanding the difference between them is essential when working with `useEffect`.

#### 1. Without a dependency array

```tsx
useEffect(() => {
  console.log('Effect executed');
});
```

When we do not provide a dependency array, React runs the Effect after every commit.

This means it runs after the initial render and after every subsequent render that React commits.

#### 2. With an empty dependency array

```tsx
useEffect(() => {
  console.log('Effect executed');
}, []);
```

An empty dependency array tells React that the Effect does not depend on changing reactive values from the component.

In normal production behavior, the Effect runs after the initial mount. However, as we will see shortly, React may perform an additional setup-and-cleanup cycle when using `StrictMode` during development.

#### 3. With dependencies

```tsx
useEffect(() => {
  console.log('Name changed:', name);
}, [name]);
```

Here, the Effect runs after the initial mount and again whenever the value of `name` changes.

The following table summarizes these situations:

| Dependency array | When the Effect runs |
|---|---|
| No array | After every commit. |
| `[]` | After the initial mount. |
| `[name]` | After the initial mount and when `name` changes. |

There is an important rule to remember: the dependency array must include the reactive values used by the Effect.

For example, if an Effect uses a state variable called `userId`, that variable should normally be included in the dependency array. Otherwise, the Effect may continue using an outdated value.

Do not think of the dependency array as a way to choose how often you want the code to run. Its purpose is to tell React which values the Effect depends on so that it can keep the external system synchronized correctly.

### Why Does React Run Effects More Than Once in Development?

When working with React, you may notice that an Effect runs twice during development, even when you provide an empty dependency array.

For example:

```tsx
useEffect(() => {
  console.log('Effect executed');
}, []);
```

You might see the message appear twice in the browser console.

This can happen because our application uses `StrictMode`.

As we learned in Workshop 1, `StrictMode` enables additional development checks that help us identify potential problems. One of these checks performs an additional setup-and-cleanup cycle for Effects when a component first mounts.

The purpose is to help us detect Effects that do not correctly manage their external operations. For example, an Effect that starts a timer but does not clean it up could accidentally leave multiple timers running.

This behavior is intentional and only applies to development checks. It is not a reason to remove `StrictMode` or try to prevent the Effect from running again.

Instead, we should make sure that our Effects are written correctly, including their setup and cleanup logic. To understand why this matters, let's look at how cleanup functions work.

## Cleaning Up Effects

Some Effects start operations that continue running after the component has finished rendering. For example, a timer may continue executing at regular intervals, an event listener may keep waiting for browser events, or a subscription may continue receiving messages.

The problem is that these operations do not necessarily stop when a component is removed from the screen. If we do not manage them properly, they can continue running even though the component that created them is no longer needed.

Imagine that we want to create a component displaying the current time and updating every second.

We could start a timer using JavaScript's `setInterval()` function:

```tsx
setInterval(() => {
  console.log(new Date());
}, 1000);
```

This creates an interval that executes its callback every second.

However, what happens when the component is removed from the screen? The timer can continue running because JavaScript does not automatically know that the React component is no longer being displayed.

If the component is displayed again, another timer may be created. We could therefore end up with multiple timers running simultaneously, even though only one clock is visible.

We need a way to stop the timer when it is no longer needed. This is where the cleanup function becomes important.

### Using a Cleanup Function

An Effect can return a function that React will execute when its current setup needs to be cleaned up.

Let's build our clock again, this time managing the timer correctly:

```tsx
import { useEffect, useState } from 'react';

function Clock() {
  const [time, setTime] = useState(() => new Date());

  useEffect(() => {
    const timerId = window.setInterval(() => {
      setTime(new Date());
    }, 1000);

    return () => {
      window.clearInterval(timerId);
    };
  }, []);

  return <time>{time.toLocaleTimeString()}</time>;
}
```

Let's understand what happens.

First, we create an interval:

```tsx
const timerId = window.setInterval(() => {
  setTime(new Date());
}, 1000);
```

Every second, the callback updates the state with the current time. React then renders the component again using the updated value, so the displayed clock changes.

Next, we return a cleanup function:

```tsx
return () => {
  window.clearInterval(timerId);
};
```

This tells React how to stop the timer when the Effect's setup is no longer needed.

There are two important situations where React runs this cleanup function.

**1. When the component is removed**

If the user navigates to another page and the clock component is removed, React runs the cleanup function and stops the timer.

**2. Before the Effect runs again**

If the Effect has dependencies and one of them changes, React first cleans up the previous Effect before running its setup again.

For example, imagine that an Effect subscribes to messages from a selected user. When the selected user changes, React should remove the old subscription and create a new one for the newly selected user.

Without cleanup, the component might continue listening to messages from a user it no longer needs.

### Understanding the Effect Lifecycle

A useful way to understand an Effect is to think of it as a process with two main operations: setup and cleanup.

During setup, we start the timer, subscription, or other external operation. The Effect then keeps that external system synchronized with the current component values. When those values change or the component is removed, the previous operation needs to be cleaned up.

For an Effect with dependencies, this process may happen several times:

```text
Component mounts
       |
       v
Effect setup (userId = 1)
       |
       v
userId changes to 2
       |
       v
Cleanup previous Effect
       |
       v
Effect setup (userId = 2)
       |
       v
Component is removed
       |
       v
Final cleanup
```

The important idea is that an Effect should not only describe how to start an external operation. It should also describe how to stop or replace that operation when it is no longer needed.

## When Should We Use `useEffect`?

Now that we understand how Effects work, we need to know when to use them.

It is tempting to put many operations inside `useEffect` simply because it runs after rendering. However, not every operation belongs in an Effect.

Remember its main purpose:

**Use `useEffect` when a component needs to synchronize with something outside React.**

Let's look at a few situations where an Effect is unnecessary.

### Calculating Values During Rendering

Imagine that our task manager contains a list of tasks, and we want to display the number of completed tasks.

We could create a separate state variable and update it using an Effect:

```tsx
const [completedCount, setCompletedCount] = useState(0);

useEffect(() => {
  setCompletedCount(
    tasks.filter((task) => task.completed).length
  );
}, [tasks]);
```

This works, but it introduces unnecessary complexity. The completed count is already available from the task collection, so we do not need to store the same information twice.

Instead, we can calculate it directly:

```tsx
const completedCount = tasks.filter(
  (task) => task.completed
).length;
```

Whenever the component renders, React calculates the number using the current task collection.

This is called **derived data**. Derived data is information that can be calculated from existing props or state.

Keeping derived values outside state avoids unnecessary synchronization and additional renders. We should generally calculate them during rendering unless there is a specific reason to store them separately.

### Responding to User Events

Another situation where an Effect is unnecessary is when we need to respond directly to a user action.

Imagine that a user clicks a button to add a product to the shopping cart. We should handle that operation inside the event handler:

```tsx
function handleAddToCart() {
  addToCart(product);
}
```

We should not create an Effect that watches the cart and tries to determine when the user added something. The event handler already knows exactly when the action happened, so it is the natural place to perform the operation.

### A Simple Rule to Remember

Before writing an Effect, ask yourself: **Does this code need to communicate with something outside React?**

The following examples help illustrate the difference:

| Situation | Use an Effect? |
|---|---|
| Calculating the number of completed tasks | No |
| Updating state after a button click | No |
| Changing the browser tab title | Yes |
| Starting a timer | Yes |
| Fetching data when a component loads | Yes |
| Subscribing to a WebSocket | Yes |
| Filtering an existing array | No |

The goal is not to use Effects everywhere. It is to use them only when they are needed.

Keeping this distinction clear makes components simpler and helps us understand which operations belong to rendering, which belong to event handlers, and which require synchronization with an external system.

## Fetching Data from an API
So far, our task manager has worked with data stored inside the browser. But imagine that we want to display tasks stored on a server instead.

How can React retrieve that information?

We use an **API request**.

An API allows two systems to communicate and exchange information. In a typical web application, the frontend sends HTTP requests to a backend server, which processes those requests and returns a response.

For example, when a user opens a task manager, the frontend may send a request asking the backend for that user's tasks. The backend retrieves the information and returns it, usually in JSON format. The frontend then uses the returned data to update the interface.

### Understanding the Request Process

When we request information from an API, the operation does not happen immediately. The browser sends the request, the server processes it, and eventually a response arrives.

During this time, the application needs to handle different situations. The request may still be running, the server may return the requested information, the returned collection may be empty, or something may go wrong.

We therefore need to represent these situations in our interface.

A common approach is to manage three pieces of information: the data returned by the API, the current request status, and any error message.

For example, we can define the possible request statuses using a TypeScript union type:

```tsx
type RequestStatus = 'loading' | 'success' | 'error';
```

This gives us a clear way to describe what is happening while the request is being processed.

### Fetch Data Using `useEffect`

Let's build a component that retrieves posts from a public demonstration API.

We will use:

```text
https://jsonplaceholder.typicode.com/posts
```

This API provides sample data that is useful for learning and testing.

First, we describe the structure of a post:

```tsx
type Post = {
  id: number;
  title: string;
  body: string;
};
```

Now we can create a component that retrieves and displays the posts:

```tsx
import { useEffect, useState } from 'react';

type Post = {
  id: number;
  title: string;
  body: string;
};

type RequestStatus = 'loading' | 'success' | 'error';

export default function PostsPage() {
  const [posts, setPosts] = useState<Post[]>([]);
  const [status, setStatus] = useState<RequestStatus>('loading');
  const [errorMessage, setErrorMessage] = useState('');

  useEffect(() => {
    async function loadPosts() {
      try {
        setStatus('loading');
        setErrorMessage('');

        const response = await fetch(
          'https://jsonplaceholder.typicode.com/posts?_limit=5'
        );

        if (!response.ok) {
          throw new Error(`Request failed: ${response.status}`);
        }

        const data = (await response.json()) as Post[];

        setPosts(data);
        setStatus('success');
      } catch (error) {
        setErrorMessage(
          error instanceof Error
            ? error.message
            : 'An unexpected error occurred.'
        );

        setStatus('error');
      }
    }

    loadPosts();
  }, []);

  if (status === 'loading') {
    return <p role="status">Loading posts...</p>;
  }

  if (status === 'error') {
    return (
      <p role="alert">
        Could not load posts: {errorMessage}
      </p>
    );
  }

  if (posts.length === 0) {
    return <p>No posts were found.</p>;
  }

  return (
    <main>
      <h1>Latest Posts</h1>

      <ul>
        {posts.map((post) => (
          <li key={post.id}>
            <h2>{post.title}</h2>
            <p>{post.body}</p>
          </li>
        ))}
      </ul>
    </main>
  );
}
```

Let's break down how this works.

### Step 1: Prepare the State

First, we create three state variables:

```tsx
const [posts, setPosts] = useState<Post[]>([]);
const [status, setStatus] = useState<RequestStatus>('loading');
const [errorMessage, setErrorMessage] = useState('');
```

Each variable has a different responsibility.

`posts` stores the information returned by the API, while `status` tells us what is happening with the request. The `errorMessage` variable stores an explanation if something goes wrong.

We initialize the status as `loading` because the component will start retrieving the posts when its Effect runs.

### Step 2: Create the Request Function

Inside our Effect, we define an asynchronous function:

```tsx
async function loadPosts() {
  // Request logic
}
```

We use `async` because retrieving data from a server takes time. An asynchronous function allows us to wait for operations such as network requests without blocking the rest of the application.

Inside the function, we use `await` when we need to wait for the result of an asynchronous operation:

```tsx
const response = await fetch(url);
```

This sends the HTTP request and waits for the response.

Once the response arrives, we can read its JSON body:

```tsx
const data = await response.json();
```

The `json()` method reads the response body and converts it into JavaScript data.

### Step 3: Check the Response

Notice this condition:

```tsx
if (!response.ok) {
  throw new Error(`Request failed: ${response.status}`);
}
```

Why do we need it?

Because `fetch()` does not automatically treat every unsuccessful HTTP response as a rejected Promise.

For example, if a server returns:

```text
404 Not Found
```

or:

```text
500 Internal Server Error
```

the `fetch()` Promise can still resolve successfully from the browser's perspective. This means that the code inside the `try` block would continue unless we explicitly check the response.

The `response.ok` property allows us to determine whether the HTTP status indicates success. If it does not, we throw an error so that the `catch` block can handle it.

### Step 4: Store the Returned Data

If the request succeeds and the response body is processed correctly, we update the state:

```tsx
setPosts(data);
setStatus('success');
```

React receives the new values and renders the component again. The interface can now display the posts returned by the API.

### Step 5: Handle Errors

Network requests can fail for different reasons. The user's internet connection may be unavailable, the server may be down, or an unexpected error may occur while processing the response.

We handle these situations using `try` and `catch`:

```tsx
catch (error) {
  setErrorMessage(
    error instanceof Error
      ? error.message
      : 'An unexpected error occurred.'
  );

  setStatus('error');
}
```

If something goes wrong, we store an error message and update the request status. The component then displays an appropriate message instead of the posts.

### Understanding the Request States

Our component now handles the different stages of an API request:

```text
Component opens
       |
       v
Status = loading
       |
       v
Send API request
       |
       v
   Is it successful?
      /       \
    Yes        No
     |          |
     v          v
  success     error
     |          |
     v          v
Display       Display
posts         error message
     |
     v
If the returned list is empty,
display an empty-state message.
```

This is how we build interfaces that respond properly to asynchronous operations. Instead of assuming that data will always be available, we describe what the user should see during each stage.

## Canceling Requests and Cleaning Up API Effects

Our previous API example works, but it has an important limitation: the request continues even if we no longer need its result.

Imagine that the user navigates away from the page while the request is still running. The browser may continue processing that request even though the component that started it has been removed.

A similar problem can happen when a request depends on a search term.

For example, imagine that the user searches for:

```text
React
```
Then quickly changes the search to:
```text
TypeScript
```

The application may send two requests. If the first request takes longer than the second, its response could arrive last and replace the newer search results.

We need a way to cancel requests that are no longer relevant.

### Using AbortController

The browser provides an API called `AbortController`, which allows us to cancel certain asynchronous operations, including `fetch()` requests.

Let's modify our previous example:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function loadPosts() {
    try {
      setStatus('loading');

      const response = await fetch(
        'https://jsonplaceholder.typicode.com/posts?_limit=5',
        {
          signal: controller.signal,
        }
      );

      if (!response.ok) {
        throw new Error(`Request failed: ${response.status}`);
      }

      const data = (await response.json()) as Post[];

      setPosts(data);
      setStatus('success');
    } catch (error) {
      if (error instanceof Error && error.name === 'AbortError') {
        return;
      }

      setErrorMessage(
        error instanceof Error
          ? error.message
          : 'An unexpected error occurred.'
      );

      setStatus('error');
    }
  }

  loadPosts();

  return () => {
    controller.abort();
  };
}, []);
```

Let's understand the important parts.

First, we create an `AbortController`:

```tsx
const controller = new AbortController();
```

This gives us an object that can control the cancellation of an asynchronous operation.

Next, we pass its signal to the request:

```tsx
{
  signal: controller.signal,
}
```

This connects the request to our controller and allows the request to be aborted through it.

Finally, we call `abort()` inside the cleanup function:

```tsx
return () => {
  controller.abort();
};
```

When React cleans up the Effect, the browser receives the cancellation signal and attempts to stop the request.

We also check whether the error was caused by cancellation:

```tsx
if (error instanceof Error && error.name === 'AbortError') {
  return;
}
```

Cancellation is expected behavior when we deliberately stop an unnecessary request. Therefore, we do not need to display it as an error to the user.

### When Is Request Cleanup Useful?

We should consider canceling requests when a component is removed while a request is running, when a user changes a search query before the previous request finishes, or when the user navigates to another record and the previous request is no longer useful.

This prevents unnecessary work and reduces the possibility of outdated responses interfering with newer results.

However, cancellation is not a complete solution to every overlapping-request problem. In more complex situations, the application may also need to track which request produced a response and ensure that only the latest relevant result updates the interface.

The main idea is simple: **when an Effect starts an asynchronous operation that is no longer needed, it should clean up that operation.**

### A Note About TypeScript and API Data

There is something important about this line from our example:

```tsx
const data = (await response.json()) as Post[];
```

We are telling TypeScript to treat the returned data as an array of `Post` objects. However, this does not mean TypeScript has checked the actual JSON received from the server.

Imagine that the server sends:

```json
{
  "message": "Something went wrong"
}
```

instead of the array of posts we expected.

TypeScript will not automatically detect this mismatch because type assertions do not validate data at runtime.

This distinction matters because information received from an external source cannot be assumed to have the structure we expect. In production applications, we should validate external data before relying on it.

Libraries such as Zod allow us to describe an expected data structure and validate the actual response at runtime.

For now, remember the difference: TypeScript checks our code during development, while runtime validation checks the actual data received from external sources.

When an application performs many API requests, tools such as TanStack Query can also help manage caching, retries, and request states. We will focus on understanding the basic React and browser mechanisms first.

## Understanding `useRef`

We have now learned how to use state to manage information and Effects to synchronize components with external systems.

However, sometimes we need to remember a value between renders without causing React to update the interface. In other situations, we need direct access to an element created by the browser.

For example, imagine that we want to focus an input field when the user clicks a button. We could try to manage this behavior using state, but state is not the right tool for accessing the actual input element.

React provides a Hook called `useRef` for situations like this.

### Accessing a DOM Element

Let's create a simple search component:

```tsx
import { useRef } from 'react';

function SearchBox() {
  const inputRef = useRef<HTMLInputElement | null>(null);

  function focusSearch() {
    inputRef.current?.focus();
  }

  return (
    <div>
      <label htmlFor="search">Search</label>

      <input
        id="search"
        ref={inputRef}
      />

      <button type="button" onClick={focusSearch}>
        Focus Search
      </button>
    </div>
  );
}
```

Let's understand what happens.

First, we create a reference:

```tsx
const inputRef = useRef<HTMLInputElement | null>(null);
```

A ref is an object that React keeps between renders. It contains a property called `current`, which holds the value we want to remember.

Initially, `current` is `null` because the input element has not yet been attached to the reference.

Next, we connect the ref to the input:

```tsx
<input ref={inputRef} />
```

After React creates the input element and attaches it to the DOM, it places the corresponding DOM element inside:

```tsx
inputRef.current
```

We can now access the input and call its `focus()` method:

```tsx
inputRef.current?.focus();
```

The optional chaining operator (`?.`) ensures that the method is only called when `current` is not `null`.

When the user clicks the button, the input receives focus.

### How Is `useRef` Different from `useState`?

Both `useRef` and `useState` allow us to keep values between renders, but they serve different purposes.

With state:

```tsx
const [count, setCount] = useState(0);
```

Updating the value using `setCount` tells React that the component needs to render again.

With a ref:

```tsx
const countRef = useRef(0);
```

We can update its value directly:

```tsx
countRef.current += 1;
```

However, changing `current` does not trigger a new render.

This is the main difference between the two Hooks.

**Use state when changing a value should update the interface. Use refs when you need to remember a value or access something without triggering a render.**

Refs are useful for accessing DOM elements, storing timer IDs, and remembering mutable values needed by event handlers.

The important thing is not to use refs as a replacement for state when the user should see the updated value on the screen.

## Creating Custom Hooks

As we build more React components, we may notice that some behavior appears in several places.

For example, multiple components may need to start and stop timers, listen for browser events, manage search delays, or read information from browser storage.

We could copy the same logic into every component, but this would create unnecessary repetition. If we later need to change that behavior, we would have to update every component containing the copied code.

React provides a solution called **custom Hooks**.

A custom Hook is a JavaScript or TypeScript function that uses React Hooks to provide reusable behavior. Its name must start with `use`, which allows React and its development tools to recognize it as a Hook.

For example:

```tsx
function useSomething() {
  // Hook logic
}
```

We can then call this custom Hook inside different components to reuse the behavior it provides.

### Example: Create a Debounced Value Hook

Imagine building a search field that sends an API request every time the user types something.

If the user types:

```text
React
```

the application might send several requests:

```text
R
Re
Rea
Reac
React
```

This creates unnecessary network requests because we usually only need the final search term.

We can reduce these requests using a technique called **debouncing**.

Debouncing means waiting for a specified period after the last change before performing an operation.

For example, if we choose a delay of 350 milliseconds, the search operation waits until the user has stopped typing for that amount of time.

Let's create a reusable custom Hook:

```tsx
import { useEffect, useState } from 'react';

export function useDebouncedValue<T>(
  value: T,
  delayMs: number
): T {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timeoutId = window.setTimeout(() => {
      setDebouncedValue(value);
    }, delayMs);

    return () => {
      window.clearTimeout(timeoutId);
    };
  }, [value, delayMs]);

  return debouncedValue;
}
```

Let's understand the important parts.

First, we create a state variable that will contain the delayed value:

```tsx
const [debouncedValue, setDebouncedValue] = useState(value);
```

Initially, it contains the same value passed to the Hook.

Next, we start a timer:

```tsx
const timeoutId = window.setTimeout(() => {
  setDebouncedValue(value);
}, delayMs);
```

When the specified delay finishes, the state is updated with the current value.

But what happens if the user types another character before the timer finishes?

The Effect runs again because `value` has changed. Before setting up the new timer, React executes the previous cleanup function:

```tsx
return () => {
  window.clearTimeout(timeoutId);
};
```

This cancels the previous timer. React then creates a new timer for the latest value.

The same process continues as the user types. Every new change cancels the previous timer and starts another one. Only when the user stops changing the value for the specified delay does the state update.

### Using the Custom Hook

Now we can use our custom Hook inside a component:

```tsx
import { useState } from 'react';
import { useDebouncedValue } from './useDebouncedValue';

function SearchPage() {
  const [query, setQuery] = useState('');

  const debouncedQuery = useDebouncedValue(query, 350);

  return (
    <main>
      <label htmlFor="search">Search Posts</label>

      <input
        id="search"
        value={query}
        onChange={(event) => setQuery(event.currentTarget.value)}
      />

      <p>Current input: {query}</p>

      <p>Search value: {debouncedQuery}</p>
    </main>
  );
}
```

Try typing something slowly and watch both values.

The current input changes immediately because it is connected directly to the state. However, the search value changes only after you stop typing for the specified delay.

We can use `debouncedQuery` as the value that triggers an API request, reducing unnecessary requests while the user is still entering text.

### Why Are Custom Hooks Useful?

The main advantage of custom Hooks is that they allow us to reuse behavior without copying the same logic into several components.

For example, we could create custom Hooks for debouncing values, reading browser storage, tracking the current window size, managing keyboard events, or connecting to a WebSocket.

One important detail is that custom Hooks share logic, not the same state instance.

For example, if two components call `useDebouncedValue`, each component gets its own state and timer. Custom Hooks do not automatically create global shared state.

We should also remember the Rules of Hooks:

- Call Hooks at the top level of React components or other custom Hooks.
- Do not call Hooks inside conditions or loops.
- Do not call Hooks inside ordinary event handlers or regular JavaScript functions.

Following these rules allows React to keep track of Hooks correctly across renders.
## Working with Browser Storage

We have now learned how to use Effects and custom Hooks to interact with external systems. Another useful browser feature we should understand is browser storage.

Imagine that a user selects dark mode in our application.

We can store the selected theme in React state:

```tsx
const [theme, setTheme] = useState('dark');
```

However, this information exists only while the application is running. When the user refreshes the page, the state returns to its initial value.

How can we remember the user's choice?

The browser provides storage features that allow websites to save information locally. Two common options are `localStorage` and `sessionStorage`.

### Understanding localStorage

`localStorage` allows us to store small pieces of information in the browser.

Unlike React state, its contents generally remain available after refreshing the page or closing and reopening the browser. The information remains stored until it is explicitly removed or cleared by the user or browser.

For example, we can store the selected theme:

```tsx
localStorage.setItem('theme', 'dark');
```

This saves a value under the key `theme`.

To retrieve it, we use:

```tsx
const theme = localStorage.getItem('theme');
```

And to remove it:

```tsx
localStorage.removeItem('theme');
```

Notice that browser storage stores values as strings. If we want to store objects or arrays, we first need to convert them into JSON.

For example:

```tsx
const user = {
  name: 'Sarah',
  age: 25,
};

localStorage.setItem('user', JSON.stringify(user));
```

To retrieve the object, we read the stored string and convert it back into JavaScript data:

```tsx
const savedUser = localStorage.getItem('user');

if (savedUser) {
  const userData = JSON.parse(savedUser);
}
```

`JSON.stringify()` converts JavaScript data into a JSON string, while `JSON.parse()` converts that string back into JavaScript data.

### Understanding sessionStorage

`sessionStorage` works in a similar way, but its information is generally kept for the lifetime of the current browser tab's page session.

For example:

```tsx
sessionStorage.setItem('currentTab', 'dashboard');
```

The value can be retrieved using:

```tsx
sessionStorage.getItem('currentTab');
```

The main difference between these two storage mechanisms is how long the information remains available and how it is shared between tabs.

| Feature | localStorage | sessionStorage |
|---|---|---|
| Survives page refresh | Yes | Yes |
| Available after closing and reopening the browser | Generally yes | No, after the page session ends |
| Shared across tabs | Yes, for the same origin | No, each tab has its own session |
| Stores values as strings | Yes | Yes |

Both options are useful for storing small pieces of information that need to remain available in the browser.

However, they should not be treated as databases.

For example, imagine that our store management application has several employees. Storing product quantities in `localStorage` would be a poor solution because each employee would have separate browser storage. Changes made by one employee would not automatically appear for everyone else.

That information should be stored on the backend, where all authorized users can access the same data.

Browser storage is more appropriate for information such as theme preferences, language preferences, small interface settings, and temporary drafts.

We should also avoid storing passwords, authentication secrets, or sensitive information in browser storage.

### Synchronizing React State with localStorage

Let's create a component that remembers the user's theme preference.

We want to achieve two things: read the previously saved theme when the component starts and save the new theme whenever the user changes it.

We can combine `useState`, `useEffect`, and `localStorage` to achieve this:

```tsx
import { useEffect, useState } from 'react';

type Theme = 'light' | 'dark';

function ThemePreference() {
  const [theme, setTheme] = useState<Theme>(() => {
    const savedTheme = localStorage.getItem('theme');

    return savedTheme === 'dark' ? 'dark' : 'light';
  });

  useEffect(() => {
    localStorage.setItem('theme', theme);

    document.documentElement.dataset.theme = theme;
  }, [theme]);

  function handleToggleTheme() {
    setTheme((currentTheme) =>
      currentTheme === 'light' ? 'dark' : 'light'
    );
  }

  return (
    <button type="button" onClick={handleToggleTheme}>
      Switch to {theme === 'light' ? 'dark' : 'light'} mode
    </button>
  );
}
```

Let's follow the process.

**Step 1: Read the saved preference.**

When the component initializes, we try to retrieve the previously saved theme:

```tsx
const savedTheme = localStorage.getItem('theme');
```

If the saved value is `dark`, we initialize the state with dark mode. Otherwise, we use light mode.

Notice that we pass a function to `useState`. This is called a lazy initializer. It allows the storage lookup to happen during initialization rather than every time the component renders.

**Step 2: Update browser storage.**

After the theme has been initialized, we use an Effect to synchronize the browser storage with the current state:

```tsx
useEffect(() => {
  localStorage.setItem('theme', theme);
}, [theme]);
```

Whenever the theme changes, React runs the Effect and saves the new value.

**Step 3: Update the browser interface.**

We also update the theme attribute on the root HTML element:

```tsx
document.documentElement.dataset.theme = theme;
```

This allows our CSS to use the selected theme:

```css
:root[data-theme='light'] {
  background: white;
  color: black;
}

:root[data-theme='dark'] {
  background: #222;
  color: white;
}
```

Now, when the user changes the theme, React updates its state, the Effect saves the preference, and the browser document receives the new theme.

When the page is refreshed, the component reads the saved preference again, allowing the application to restore the user's previous choice.

This is another example of synchronizing React with an external system.

**Important:** This example is intended for a client-rendered application, such as the Vite project used in this course. In applications that also render on a server, browser features such as `localStorage` and `document` need additional handling because they are not available on the server.
## Bringing Everything Together: The API-Powered Search

We have now explored several ways to interact with the outside world. We can retrieve data from APIs, cancel unnecessary requests, use refs to access browser elements, create reusable Hooks, and store user preferences.

Let's connect some of these ideas in one practical example.

Imagine that we want to build a search page that retrieves information from an API. The interface should contain a search input and display matching results.

However, we do not want to send a request for every character the user types. As we saw earlier, this could generate several unnecessary requests.

Instead, we will use the `useDebouncedValue` custom Hook to wait until the user stops typing before sending the request.

The complete process will look like this:

```text
1. The user enters a search term.
                 |
                 v
2. React updates the input state.
                 |
                 v
3. useDebouncedValue waits for the user
   to stop typing.
                 |
                 v
4. The debounced search value changes.
                 |
                 v
5. An Effect sends an API request.
                 |
                 v
6. The application displays a loading state.
                 |
                 v
7. The API returns a response.
                 |
                 v
8. The interface displays the results
   or an appropriate message.
```

This design combines several concepts from the workshop. Controlled inputs manage the user's search term, custom Hooks handle debouncing, and Effects trigger the API requests when the debounced value changes.

We also need to handle situations where the user changes the search term before the previous request finishes. In that case, we should cancel the obsolete request so that outdated results do not replace the newer ones.

This example brings together controlled inputs, state management, custom Hooks, Effects, dependency arrays, API requests, request cancellation, and conditional rendering.

## Workshop Recap

In this workshop, we moved beyond managing information inside React and explored how components interact with external systems. Let's review the main concepts and how they connect.

### Effects and Synchronization

`useEffect` allows a component to synchronize with external systems. Its dependency array tells React which reactive values the Effect uses and when it needs to run again.

An Effect without a dependency array runs after every commit, while an empty dependency array normally makes it run after the initial mount. When dependencies change, React cleans up the previous Effect before setting up the next one.

Cleanup functions are important because they allow us to stop timers, remove event listeners, cancel requests, and disconnect subscriptions when they are no longer needed.

We should also avoid using Effects for calculations that can be performed during rendering or operations that belong directly inside event handlers.

### APIs and Asynchronous Operations

APIs allow the frontend and backend to exchange information. We use `fetch()` to send HTTP requests, while `async` and `await` make asynchronous operations easier to read and manage.

Because unsuccessful HTTP responses do not automatically cause `fetch()` to reject, we should check `response.ok` before processing the returned data.

A good interface should also handle loading, success, empty, and error states rather than assuming that every request will succeed.

When a request is no longer needed, `AbortController` allows us to cancel it. We should also remember that TypeScript type assertions do not validate external JSON at runtime.

### Refs and Custom Hooks

`useRef` allows us to store values between renders without triggering a new render. It is particularly useful when accessing DOM elements or keeping mutable values such as timer IDs.

Custom Hooks allow us to extract reusable stateful logic from components. Their names must start with `use`, and they must follow the Rules of Hooks.

Unlike global state solutions, custom Hooks do not automatically share the same state between components. Each component that calls a custom Hook receives its own Hook state.

### Browser Storage

`localStorage` stores information that generally survives page reloads and browser restarts, while `sessionStorage` stores information for the current page session.

Both mechanisms store values as strings, so we use `JSON.stringify()` and `JSON.parse()` when working with objects.

Browser storage is useful for small preferences and interface settings, but it should not replace a backend database or be used to store sensitive information.
